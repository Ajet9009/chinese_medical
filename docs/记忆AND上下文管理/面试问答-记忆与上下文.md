## Q1：为什么 Agent 要做分层记忆？直接把历史塞进 Prompt 不行吗？

**答：**

可以，但撑不住生产：

1. **成本与延迟**：全文回传随轮次线性涨 Token。  
2. **隔离**：多用户/多会话不能共用一个大字符串。  
3. **跨会话**：关掉浏览器后偏好仍要在。  
4. **可控遗忘**：用户改偏好时要覆盖旧事实，而不是越积越多矛盾句。

所以我们拆：**短期会话窗口（Redis）+ 长期事实向量（Milvus）+ 结构化画像（MySQL）**，拼 Prompt 前再做 Token 预算压缩。

---

## Q2：一次 Ask 里记忆怎么读写？

**答：**

```
Ask 前：_read_memory → get_context（长期检索 + 画像 + 短期 → fit_budget）
Ask 中：LangGraph
Ask 成功后：_write_memory → add_message(user/assistant)
失败 500：不写记忆
```

身份来自 Header：`X-User-ID` / `X-Session-ID`（Streamlit 同样传递）。

---

## Q3：短期记忆键为什么是 user_id + session_id？

**答：**

- 只有 session → 同 session 字符串会**串用户**（我们修过这个缺陷）。  
- 只有 user → 多标签/多会话**串会话**。  
- 合在一起：会话内连续对话；用户级隔离；新 session 短期清空，长期仍可按 user 召回。

键格式：`mem:short:{user_id}:{session_id}`。

---

## Q4：滑动窗口怎么实现？「20」是 20 轮吗？

**答：**

Redis List：`LPUSH` 新消息 → `LTRIM` 只留最近 N 条 → `EXPIRE` TTL。  
配置名是 `short_term_rounds`，实现上是 **最多 N 条 Message**。  
每轮成功通常写 user + assistant 两条，所以满窗口大约是 **N/2 轮** 完整问答。面试别说成「严格 20 轮」。

## Q5：【关键】上下文压缩怎么做？和 LTRIM 有什么区别？

**答：**

**必须分清两层裁剪：**

| 机制 | 位置 | 裁什么 | 何时触发 |
|------|------|--------|----------|
| LTRIM | Redis 写入 | 消息**条数** | 每次 append |
| ContextCompressor.fit_budget | 拼 Prompt | **Token 预算** | get_context 时 |

压缩逻辑（`ContextCompressor`）：

1. 预算默认 4000 token（tiktoken）。  
2. 先为长期+画像+当前输入预留额度。  
3. 短期能放下就全放。  
4. 放不下：保留最近原文，更早内容 **LLM 摘要**；摘要失败再截断。

**取舍：** 不每请求都摘要（费钱），只在超预算时摘要；不裸截断当主策略（丢语义）。

这是记忆模块的**关键亮点**，建议主动讲。

## Q6：【关键】Token 压缩预算如何定？不同预算有什么影响？怎么评判？

**答：**

### 如何定预算

不是拍脑袋写死，而是三步推导：

1. **模型硬上限**：上下文还要留给系统 Prompt、图谱/Cypher 结果、本轮推理与输出；记忆只能占其中一块「软配额」。  
2. **记忆软预算**：对应 `MemoryConfig.token_budget`（我们默认 **4000**，tiktoken `cl100k_base`）。`fit_budget` 会先扣长期+画像+当前输入，**剩余**再给短期。  
3. **用真实分布校准**：看记忆前缀长度分布、摘要触发率、Ask 延迟与费用，把默认值调到拐点；支持配置调整，而不是神圣数字。

预算和 Redis `LTRIM` 无关：LTRIM 管**条数**；`token_budget` 只管**拼进 Prompt 前**压不压、压多少。

### 不同预算的影响

| 预算偏低（如 1k–2k） | 预算偏高（如 8k–16k） |
|----------------------|------------------------|
| 更常触发 LLM 摘要，多轮指代易丢 | 少摘要，保留更多原文 |
| Token / 延迟 / 费用更低 | 费用与延迟升高 |
| 更依赖长期+画像 | 短期噪声更易干扰答题 |

### 怎么评判（可复现，不靠感觉）

1. **效果**：固定评测集（短问答、长多轮、改偏好、寒暄）上的正确率 / 指代消解；是否「忘掉上一轮」或「被旧闲聊带偏」。  
2. **成本与性能**：记忆相关 Token 的 P50/**P95**；摘要触发率；Ask 耗时 **P95**（`elapsed_ms` / Langfuse latency）。  
3. **稳定性**：摘要失败降级为截断的比例应很低。  
4. **方法**：扫描 `token_budget ∈ {1500, 4000, 8000}`，看效果曲线与成本曲线的**拐点**作为生产默认。

**P95 看什么：** 把样本排序后落在 95% 位置的值——反映**尾部体验**（100 次里约 5 次更差）。调预算时盯 Ask **延迟 P95** 和记忆 **Token P95**，比看平均值更能抓「偶尔很慢/很贵」。

**30 秒收束：**  
好预算 = 评测效果达标，且摘要率、Token P95、延迟 P95 可接受；不是越大越好。

## Q7：长期记忆存什么？怎么防幻觉？

**答：**

存三元组 `subject-predicate-object`，并带：

- `source`：来自哪句用户话（可追溯）  
- `timestamp`：写入时间  

检索是语义向量召回，不是模型「凭空想起」。面试可说：长期记忆是**带出处的结构化事实**，不是又一次自由生成。  
（补充：`source` 默认存库备查；当前拼 Prompt 主要用主谓宾，不强制注入 `source`。）

---

## Q8：信息冲突和遗忘怎么处理？

**答：**

LLM 抽取时带 `action=set|delete`。

- `delete`：Milvus 删同 subject+predicate；画像对应字段清空。  
- `set`：**先删旧再写新**（同 s+p 唯一），例如偏好从「清淡」改成「温补」。

审计表会留下 `forget` / `triple_upsert` / `profile_upsert`。

---

## Q9：长期抽取为什么异步？队列满了怎么办？

**答：**

抽三元组要调 LLM + embedding，若同步会拖长 Ask P99。  
默认丢进有界线程池；信号量控制队列长度，**满则丢弃并打日志/审计**，保证主问答不被拖死。  
测试可用 `wait_extract=True` 强制同步。

局限：极端高峰可能丢抽取 → 画像/长期暂时不全；可后续换消息队列做削峰重试。

---

## Q10：用户画像和长期记忆为什么都要？

**答：**

- **Milvus**：语义检索「和当前问题相关的事实」。  
- **画像**：固定键（偏好/身份/计划）O(1) 读出，Prompt 里稳定出现。

画像是长期的结构化投影；不是第二套互相矛盾的真相源——写入路径都经 `_apply_triple`。

## Q11：降级策略是什么？

**答：**

| 依赖 | 降级 |
|------|------|
| Redis | 内存 ShortTerm（进程内） |
| Milvus | `data/memory/long_term.json` |
| MySQL 画像 | `profile.json` |
| MySQL 审计 | `memory_audit.jsonl` |
| 记忆整体初始化失败 | API 继续答，无记忆 |

工厂：`create_memory_manager` / `_create_*_store`。`/health` 可看各层是否 ok。

## Q12：是否达到生产级？你会怎么说局限？

**答：**

**达标部分：** 隔离、TTL、窗口、脱敏、异步抽取、冲突遗忘、审计、降级、健康检查、隔离单测。  

**未齐：** Redis 高可用、失败重试/幂等、图失败也落对话、字段加密与用户删除权 API、专项压测报告。  

一句话：**可上线的企业级雏形**，不是完整记忆中台。

---

## Q13：和 Langfuse / 数据飞轮怎么配合？

**答：**

记忆解决「对话状态与个性化」；Langfuse 解决「可观测与评估飞轮」。  
Ask 路径上：记忆读写失败只打 warning，不阻断；Langfuse 仍可对本次问答采样打分。  
二者解耦：记忆坏了问答可降级；观测坏了业务仍可用。
