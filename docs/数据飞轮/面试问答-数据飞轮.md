## Q1：为什么 LLM 应用必须做可观测性和数据飞轮？传统单测不够吗？

**答：**

传统软件是确定性的：输入 → 输出可断言。LLM 应用是概率性的：同一问题今天答对、明天可能答偏，单测「字符串相等」几乎失效。

所以需要三件新东西：

1. **可观测性**：看不到模型内部，只能看输入/输出/中间节点/token/耗时/成本。  
2. **评估**：把「好不好」变成可量化指标。  
3. **数据飞轮**：用生产真实 Bad Case 固化成数据集，每次改 prompt/模型都在同一套题上回归，提升才上线、退化就回滚。

一句话：大模型上线只是开始，**数据飞轮才是持续优化的引擎**；Langfuse 在我们系统里是「数据沉淀池」，不是装饰性日志。

## Q2：你们项目里的数据飞轮闭环具体怎么跑？

**答：**

五步闭环（与 `docs/数据飞轮/observability-data-flywheel.md` 一致）：

```
生产请求
  → ① 自动评分（score_auto）+ ② 动态/强制采样
  → Bad Case（tag: forced-sampling）
  → ③ 数据回流（build_eval_dataset.py → Dataset）
  → ④ 回归实验（run_experiment：baseline vs optimized）
  → ⑤ 用户反馈（POST /feedback → user_feedback score）补充 Bad Case
  → 优化 Prompt/模型后回生产，循环
```

演示脚本 `_000_demo/demo_flywheel.py` 把 1→5 串成可复现流程，便于面试时对着 Langfuse UI（Traces / Scores / Datasets / Runs）讲。

## Q3：为什么要有 baseline？baseline 什么时候生成？

**答：**

**为什么需要：**  
优化后的分数单独看没有意义。没有对照组，你无法回答三个问题：

1. 比改之前好了多少？  
2. 某个指标涨了，是否牺牲了另一个指标？  
3. 该上线还是该回滚？

我们真实跑过分：`answer_quality` 从 0.749 → 0.777（+3.7%），但 `cypher_generated` 从 1.000 → 0.900（-10%）。**有得有失，正是 baseline 对比的价值**——不靠感觉，靠数据发现副作用。

**何时生成：**  
在「数据集已固化、任何优化动手之前」，用**当前生产配置**在同一数据集上跑一次 experiment，`run_name=baseline`。

对应演示顺序（`demo_flywheel.py`）：

1. 制造/拉取 Bad Case  
2. 回流成 `bad-cases` 数据集  
3. **跑 baseline（当前 prompt）** ← 此时生成  
4. 改 `answer_generation` prompt  
5. 再跑 `optimized`，与 baseline 对比  

生产实践里：每次打算改 prompt/模型前，都可以再跑一版「改动前」作为该次变更的 baseline；长期 golden set 尽量少改题面，只增不乱改。

## Q4：你做过什么可观测性？怎么做到零侵入？

**答：**

给中医问答接了 Langfuse 全链路：

| 对象 | 粒度 | 内容 |
|------|------|------|
| Trace | 一次 `/ask` 请求 | request_id / session_id / user_id / version |
| Span | 一个 LangGraph 节点 | 节点名 / 输入输出 / 耗时 |
| Generation | 一次 LLM 调用 | model / tokens / latency / cost / TTFT |

**零侵入做法：** 自定义 `_TraceCallbackHandler`，通过 `config={"callbacks": [handler]}` 透传进图；`_004_langgraph_more_nodes/` 业务节点代码不改。

**为什么不用官方 CallbackHandler：** Langfuse v2 官方 handler 与 LangChain v1.x 路径不兼容；我们直接调 `client.trace/span/generation`。

**真实坑：** LangGraph 节点在 callback 的 `serialized` 里 `name=None`。节点 Span 必须在 `_005_fastapi/main.py` 的 `astream_events` 循环里用 `event['name']` 调 `start_node_span` / `end_node_span`。这是落地细节，面试里讲出来比背概念更有说服力。

**降级：** 初始化失败或上报失败只打 warning，不阻断主问答。

## Q5：怎么控制观测成本？动态采样怎么设计？

**答：**

矛盾：全量采集 → 存储/ClickHouse 成本爆炸；固定抽 10% → 漏掉故障现场。

**分层采样：**

- 正常请求：`LangfuseManager.should_sample()`，由 `LANGFUSE_SAMPLE_RATE` 控制（生产常用 0.1）。  
- 异常类请求：请求结束后 `_check_force_sample` 判定，命中则 `record_summary_span` **强制**记一条，tag=`forced-sampling`。

强制条件（`main.py`）：

- 耗时 > 30s → `slow_request`  
- Cypher 重试次数 > 0 → `cypher_retry`  
- 中医意图但无 Cypher → `no_cypher`  
- 空回答 → `empty_answer`  
- 图执行异常 → `exception`

**工程取舍（必须主动说）：**  
Langfuse v2 不支持「先全量写、事后按 sampled 丢弃」。所以我们是：

> 请求开始时按概率决定是否挂完整 callback；若未命中采样但事后判定为 Bad Case，则**补记摘要 trace**（不重跑图）。

代价：强制采样拿到的是摘要现场，不是完整七节点 span 回放。收益：控成本 + 不丢故障线索。企业里这是可接受的折中。

## Q6：Bad Case 怎么筛？怎么变成评估数据集？

**答：**

**筛选：** 生产侧强制采样打上 `forced-sampling`；也可叠加用户 👎（`user_feedback=0`）。

**回流：** `python common/build_eval_dataset.py --name bad-cases`

1. `fetch_traces(tags="forced-sampling")`  
2. 从 trace.input 抽 `user_question` / `question`  
3. `sanitize` 脱敏后 `create_dataset_item`，并挂 `source_trace_id`  
4. 在 Langfuse UI → Datasets 可见

**企业级注意点：**

- 数据集是 **golden set**：题面尽量稳定，否则基线不可比。  
- 回流脚本默认不写「标准答案」——当前设计以「真实难例」驱动回归，评分靠规则/启发式/Judge，而不是字符串匹配。若要做更严的正确性，可后续人工标注 `expected_output`。  
- 这是诚实边界：我们优先把「生产真实失败」固化，而不是先造一堆合成题。

## Q7：怎么评估模型效果？三层评分怎么分工？

**答：**

生产请求结束（且命中采样、有 handler）时调 `EvalManager.score_auto`：

| 层 | 指标 | 能判断什么 | 成本 | 何时用 |
|----|------|------------|------|--------|
| 规则型 | `cypher_success` / `retry_count` / `answer_nonempty` | 有没有、成不成功、重试几次 | 几乎免费 | 每次采样请求结束自动打 |
| 启发式 | `answer_quality`（长度归一化，demo 实验里用） | 详细度粗信号 | 免费 | 回归实验对比趋势 |
| LLM-as-Judge | `judge_accuracy` / `judge_completeness` / `judge_relevance`（0–10） | 对不对、全不全、相不相关 | 每次几百 token | **回归/抽检**，不在每次线上请求都调 |

**取舍：**  
规则型兜底快；长度启发式会「长≠好」；Judge 接近人评但贵且有自身偏差。所以生产线上用规则型，精细质量放到实验与抽检。

**Judge 真实对比（demo_judge）：**

| 问题 | 回答 | accuracy | completeness | relevance |
|------|------|----------|--------------|-----------|
| 四君子汤功效 | 「补气。」 | 0 | 0 | 0 |
| 四君子汤功效 | 详细完整 | 10 | 10 | 10 |
| 人参性味归经 | 「具体不知道」 | 6 | 1 | 4 |
| 人参性味归经 | 准确完整 | 9 | 7 | 9 |

启发式长度分区分不了敷衍与完整；Judge 可以。这是加 LLM-as-Judge 的工程理由。

## Q8：回归实验怎么跑？跑分结果在哪里看？跑完分怎么「优化落地」？

**答：**

**怎么跑：**

```bash
python common/run_experiment.py --dataset bad-cases
# 或演示：python _000_demo/demo_flywheel.py
```

`EvalManager.run_experiment`：对每个 dataset item `item.observe(run_name=...)` → `task_fn`（调 `graph.invoke`）→ `eval_fn`（打分）。

**结果在哪看：**  
Langfuse UI → **Datasets → bad-cases → Runs**，对比 `baseline` 与 `optimized` 各 score 的均值/分布。

**如何达到优化效果（关键说清因果链）：**

1. 用 baseline 锁定当前能力。  
2. 针对 Bad Case 改 **Prompt**（我们把 `answer_generation` 放在 Langfuse，改完约 60s 缓存生效，无需发版重启）或换模型。  
3. 同一数据集再跑 optimized。  
4. **多指标一起看**：某一维涨、另一维跌 → 不能盲目上线。  
5. 达标才把 production label 的 prompt 固化；不达标回滚到上一版 prompt。

这就是把「凭感觉调 prompt」改成「用数据说话」的工程闭环。  
**何时回流 / 何时回归 / 何时上生产** 见下一题 Q9（企业调度视角）。

## Q9：真实企业落地里，何时触发数据回流、回归实验、上生产？

**答：**

三件事**不是每个请求都做**，按触发条件分层。一句话：

> **在线负责发现问题，回流负责固化问题，回归负责验证改法，上生产负责受控放量。**

| 动作 | 性质 | 典型频率 |
|------|------|----------|
| 采样 + `score_auto` | 在线、近实时 | 每个命中采样的请求 |
| **数据回流** | 离线批处理 | 按天/按周，或积够量、告警时 |
| **回归实验** | 离线、有成本 | 有候选变更时，或发版门禁 |
| **上生产** | 发布决策 | 实验达标 + 灰度/签核之后 |

### 数据回流（Bad Case → Dataset）何时触发

对应脚本：`common/build_eval_dataset.py`（生产挂 cron / 调度，而非请求内同步执行）。

1. **定时批跑（最常见）**：每天/每周拉 `forced-sampling` + 👎 反馈，清洗后写入 Dataset。  
2. **量够了再回流**：新增强制采样 ≥ N 条，或某类 `reason`（如 `no_cypher`）暴涨，避免两三条就搅乱集版本。  
3. **质量事件驱动**：空答率、Cypher 失败率、P95、👎 超阈值，或事故复盘后定向回流专项集。  
4. **人审后再进 golden（建议）**：自动回流是候选；进稳定评估集前抽样去噪、脱敏、去重。

**不会做：** 每个线上请求当场回流。在线只打 tag/score，回流异步。

### 回归实验（baseline vs candidate）何时触发

对应：`run_experiment` / `demo_flywheel` 里的 baseline → optimized。

1. **有候选变更时（主路径）**：改 Prompt / 换模型 / 改图节点或 schema → **先**用当前生产配置跑 baseline（或沿用最近一次）→ **再**跑 candidate。  
2. **发版门禁**：merge/发布前对固定 Dataset 自动跑；不达标阻断或需签核。  
3. **定期健康检查**：例如每周用当前 production 跑一遍 golden，抓静默退化（模型行为变、缓存脏）。  
4. **数据集版本升级后**：`bad-cases-v1` → `v2` 时先对新集建**新 baseline**，旧 run 不可直接横比。

**不会做：** 每次线上请求全量回归；LLM-as-Judge 也不建议全量在线打。

### 上生产何时触发

上生产 = 真正服务用户（Prompt `label=production`、模型路由、服务发版等）。

硬门槛建议：

1. **相对 baseline 多指标达标**：核心指标不退化或在带宽内（不能只看回答变长）。本仓库真实例子：`answer_quality +3.7%` 但 `cypher_generated -10%` → 不能盲目上线。  
2. **覆盖相关集**：通用 golden + 本次 Bad Case 专项集都过。  
3. **灰度/金丝雀**：小流量看延迟、错误率、👎、强制采样量，再全量。  
4. **人签核（高风险域）**：中医话术等自动分过了仍可业务/安全审一轮。  
5. **回滚就绪**：Prompt 上一 version / 路由 / feature flag 可秒切。

上线后继续在线采样 → 新 Bad Case 再回流，飞轮才转。

### 时间线（面试可画）

```
持续在线:  请求 → 采样/强制采样 → score_auto → (偶发) 用户反馈
                │
定时/告警:        └→ 【数据回流】写入/更新 Dataset
                          │
有候选变更时:              └→ 【回归】baseline(当前生产) vs candidate
                                  │
指标达标+灰度+签核:                └→ 【上生产】切 production
                                          │
                                          └→ 再观察 → 新 Bad Case → 回流…
```

### 与本仓库演示的差别（主动说更可信）

`_000_demo/demo_flywheel.py` 为讲清闭环，把回流→baseline→改 prompt→回归**压在一次脚本里**。企业会拆开：回流靠调度、回归靠变更/门禁、上生产靠指标+灰度+回滚。能力模型相同，调度粒度不同。

## Q10：Prompt 为什么放到 Langfuse？和数据飞轮什么关系？

**答：**

提示词从硬编码迁到 Langfuse：`get_prompt(name, fallback, label="production")`，失败回落本地 fallback。

价值：

- 改 prompt 不用重新部署服务  
- 版本与 label 可回滚  
- 与 experiment 天然配合：改 candidate prompt → 跑 run → 对比 baseline → 达标再切 `production`（见 Q9）  

飞轮里「优化动作」经常就是改 prompt；观测与评估在 Langfuse，prompt 也在 Langfuse，形成同一套工具链，减少「改了配置却对不上实验」的混乱。

## Q11：Trace 写不进 ClickHouse 怎么排查？（展示系统化思维）

**答：**

我们真实踩过「只读降级、UI 看不到 trace」。排查链（面试按层说）：

1. **服务日志**：Langfuse 报 Read from postgres only → 只读降级。  
2. **配置**：v2.95 架构下 trace 依赖 ClickHouse，compose 缺 CH。  
3. **网络**：拉镜像被墙 → 配代理。  
4. **认证**：账号密码要用 `CLICKHOUSE_USER/PASSWORD` 环境变量，不能只塞 URL。  
5. **权限**：Windows bind mount 权限问题 → 换 named volume。  
6. **进程**：FastAPI `--reload` 导致 SDK 状态混乱 → 去掉 reload，并在请求结束显式 `flush`。

体现的是：**分层定位，每层有验证手段**，而不是「重启碰运气」。

## Q12：观测对业务的侵入性和可靠性怎么保证？

**答：**

两层策略：

1. **异步上报**：SDK 缓冲 + 请求结束 `flush(timeout=5)`，业务路径不因观测阻塞过久。  
2. **合理采样**：正常请求按比例；异常全量摘要。  

可靠性：

- `LANGFUSE_ENABLED=false` 或密钥缺失 → 全局禁用 tracing，问答仍可用。  
- handler 创建/span 更新失败只 warning。  
- 记忆层 Redis/向量失败同样降级，不挡主流程。

企业级底线：**观测挂了，业务不能挂。**

## Q13：记忆系统和数据飞轮是什么关系？信息冲突怎么处理？

**答：**

记忆（`_008_memory`）解决「多轮上下文与用户偏好」；飞轮解决「系统能力是否在变好」。二者正交但都要可观测。

记忆三层：短期 Redis（session）+ 长期向量事实（user）+ 结构化画像。

**信息冲突：** 三元组 `(subject, predicate)` 唯一；写入前删旧值；否定意图直接遗忘。否则用户改过的偏好会继续污染回答，飞轮里也会反复出现同类 Bad Case。

Token 超预算时摘要压缩，而不是硬截断——避免「丢关键事实却假装还记得」。

## Q14：如果面试官追问「你们是不是只是套了个 Langfuse？」怎么回应？

**答：**

不是装 SDK 那么简单。我们做了四件「自托管 + 业务耦合」的落地：

1. **兼容性适配**：自研 CallbackHandler，解决 v2 × LangChain v1 不兼容。  
2. **采样策略产品化**：强制条件写进 API 层，与中医图状态字段绑定（retry / cypher / 空答 / 慢请求）。  
3. **评估闭环工程化**：回流脚本 + experiment API + baseline/optimized 对比流程可脚本化复现；企业侧再按 Q9 做调度与发版门禁。  
4. **成本字段打通**：Generation 写 `cost_details`（注意不是错误的 `cost` 参数），便于算账。

同时承认边界：强制采样是摘要、线上未全量 Judge、golden 集 expected 仍可加强、演示脚本尚未拆成独立调度——这是下一阶段演进，不是隐瞒。
